# M3: Torrents — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Download magnet links and `.torrent` files through the same `Engine`, queue and CLI as HTTP downloads, with file selection, seeding rules (ratio and time), torrent speed limits, and byte-perfect resume after a restart.

**Architecture:** A new `torrent` module in `taurus-core` wraps one lazily started `librqbit::Session` (the `TorrentHub`). A torrent job is a job row with `kind = Torrent`; its runner task drives the librqbit handle, polls stats every 250 ms, reports progress through the existing `JobMsg` channel, and reports a new `Seeding` phase that frees its queue slot. Our SQLite store stays the source of truth: librqbit's own JSON persistence is kept only for fastresume and is reconciled against the store on start. Pure logic (input classification, path safety, output folders, seeding policy, rate splitting, error mapping) lives in small unit-tested files.

**Tech Stack:** as M2, plus `librqbit = { version = "9.1", default-features = false, features = ["rust-tls"] }` (Apache-2.0; checked: it compiles against our reqwest 0.13.5, no OpenSSL). Test helpers additionally use `sha1` (bencoded test torrents).

**Spec:** `docs/superpowers/specs/2026-10-27-taurus-v2-design.md` — sections 3 (torrents in v1.0), 6.4, 7 "Torrents", 8 ("Torrents: two librqbit sessions on localhost"), 9 row M3.

## Global Constraints

- All earlier Global Constraints hold (no internet in tests, CI on 3 OSes with fmt + clippy `-D warnings`, `rust-version = "1.89"`, durability, never overwrite).
- One `librqbit::Session` per `Engine`, started on the first torrent job (add or restore), never for HTTP-only use.
- librqbit always downloads pieces in order (its README), so there is no "download in order" setting; spec 6.4's toggle is satisfied by default. Note this in the spec when the plan lands (Task 9).
- Torrent defaults: stop sharing at ratio 1.0, no time limit, no upload limit, no torrent-only download limit, `max_active` torrents 3, peer limit = librqbit default, random listen port, UPnP on, DHT on.
- `stop_ratio = Some(0.0)` means "stop as soon as the download finishes" (uploading while downloading is how BitTorrent works and is not prevented). `None` means never stop.
- Ratio = uploaded bytes / total bytes of the **selected** files. Uploaded bytes are counted by us across restarts (librqbit's counter is per session).
- Seeding jobs do not count toward any `max_active` limit and do not block `QueueIdle` / when-done.
- Speed presets: the global rate is split evenly between HTTP and torrents only while both kinds are downloading; a torrent-only `download_limit_bps` further caps the torrent side. Uploads use `upload_limit_bps` only.
- Port, DHT and UPnP changes apply the next time the session starts (engine reopen); the CLI says so when they are set.
- Test networking: tests disable DHT, trackers, local service discovery and UPnP, listen on `127.0.0.1:0`, and connect peers through an explicit initial-peer list.

## Review Focus

1. Restarting the engine halfway through a torrent must resume from what is on disk, not download it again and not corrupt it. Test: Task 8 `restart_resumes_without_redownload` (seeder upload < 1.5 × size, hash matches).
2. Removing a torrent job with files must delete only that torrent's files (and its own folder when we created it), never a neighbour's file in the same save folder. Test: Task 8 `remove_with_files_touches_only_its_files`.
3. Two torrents with the same name saved to one folder must not mix: the second goes into `Name (1)`. Test: Task 8 `same_name_twice_gets_suffix_folder`.
4. A magnet link nobody is sharing must not hang forever: after the metadata timeout the job is Waiting with `NoPeers`, then retried. Test: Task 8 `magnet_without_peers_waits`.
5. Seeding must not hold a download slot or the when-done action. Test: Task 8 `seeding_frees_slot_and_does_not_block_idle`.

### Task 5: Torrent job runner

**Files:**
- Create: `crates/taurus-core/src/torrent/job.rs`; Modify: `timing.rs` (add `torrent_metadata_timeout`: 120 s default, 2 s in `fast_for_tests`; `torrent_poll`: 250 ms), `engine/actor.rs` (`JobMsg::Seeding { id }`, `JobMsg::TorrentStats { id, view: TorrentView }`)

**Interfaces:**
- Produces:

```rust
pub struct TorrentJobContext {
    pub id: JobId, pub hub: std::sync::Arc<TorrentHub>, pub store: Store, pub timing: Timing,
    pub settings: TorrentSettings, pub space: SpaceSource /* existing test override type */,
    pub cancel: tokio_util::sync::CancellationToken,
    pub msgs: tokio::sync::mpsc::UnboundedSender<JobMsg>,
}
pub async fn run_torrent_job(ctx: TorrentJobContext) -> JobOutcome;
```

Algorithm:
1. Load the job. If `torrent_meta` is None: `hub.list_files(source, timing.torrent_metadata_timeout)` → store `info_hash`, `torrent_meta`, file name (torrent name), `total = selected_total`; `files::check_paths` (UnsafeTorrent → Failed). If another job already has this `info_hash` → Failed(AlreadyAdded).
2. Pre-flight: `check_fits(output, total - progress, largest selected file)` (FAT32 uses the largest selected file).
3. `hub.add_bytes(meta, output, only_files, paused = false)` (or `unpause` if the session already has it).
4. Poll `handle.stats()` every `torrent_poll`: send `JobMsg::Progress { downloaded: progress_bytes, total: Some(total_bytes), speed_bps: live.download_speed.as_bytes() }` and `JobMsg::TorrentStats`; count uploaded as `job.uploaded + (stats.uploaded_bytes - baseline)` (baseline = first poll's value; if the counter drops, re-baseline) and `commit_torrent_progress` every 5 s and at exit. `stats.error = Some(msg)` → Failed(`classify_torrent_error`).
5. When `stats.finished`: `mark_downloaded` each selected file (url = the magnet or torrent URL), set `seed_started_at` (if unset), send `JobMsg::Seeding { id }`.
6. Seeding: keep polling; when `SeedPolicy::should_stop(uploaded, total, now - seed_started_at)` → `hub.pause` → return `Completed(output)`. `stop_ratio = Some(0.0)` stops at step 5 without seeding.
7. Cancel token (pause/shutdown/remove): `hub.pause`, final commit, return `Paused`.

### Task 6: Engine integration

**Files:**
- Modify: `crates/taurus-core/src/engine/{mod.rs,actor.rs,jobs.rs,schedule.rs,settings.rs}`

**Interfaces:**
- Produces:

```rust
// AddRequest gains:

    pub async fn torrent_files(&self, input: &str) -> Result<TorrentInfo, CoreError>; // for the file picker; uses the metadata timeout
```

Decisions:
- `add` calls `torrent::source::classify(req.url)`. `Http` keeps the M2 path. `Magnet`/`TorrentUrl`/`TorrentFile`: a `TorrentUrl` is fetched with the job client (≤ 10 MiB, must parse as a torrent); a `TorrentFile` is read from disk. If the info hash is known (magnet or parsed bytes) and `find_by_info_hash` finds a job → `Err(AlreadyAdded)` with no new row. Name = torrent name (or magnet `dn`, else the info hash). `dest_dir` must exist (FolderUnavailable as for HTTP). The job is inserted `kind = Torrent`, `Queued`.
- Scheduler: HTTP jobs count against `settings.max_active`; torrent jobs in `Downloading` count against `settings.torrent.max_active`; `Seeding` jobs count against neither. On `JobMsg::Seeding` the job's state becomes `Seeding` (stored, `JobUpdated`), it leaves the downloading count (its cancel token stays in `running`), and the scheduler runs. `QueueIdle` ignores Seeding jobs.
- `pause` of a Seeding job → `Paused` (sharing stops); `resume` of a completed-by-policy torrent is a no-op (Completed).
- `remove(id, delete_files = true)` for torrents → `hub.delete(info_hash, true)`, then remove the folder we created (`output_dir` that is not `dest_dir` itself) only if it is empty afterwards.
- Engine open: if any torrent job exists, start the hub and `reconcile`; torrent jobs left `Downloading` or `Seeding` come back `Queued` (M2 rule for interrupted jobs) — a finished torrent is re-checked by fastresume and goes straight to Seeding.
- Limits: on every change of settings or of which kinds are downloading, apply `split_rate` to the shared HTTP `Limiter` and `torrent_rate` + `upload_limit_bps` to `hub.set_limits`.
- `JobMsg::TorrentStats` updates `JobView.torrent` (no extra event beyond `Progress`; the view is visible in `snapshot()` and in the next `JobUpdated`).
