# M5: Video Sites and Media — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Download video and audio from sites yt-dlp supports — single videos, playlists and live streams — from Simple mode and the CLI, with yt-dlp, ffmpeg and Deno downloaded, verified, updated and rolled back automatically.

**Architecture:** Two new core modules. `tools` installs and maintains the three external programs under `data_dir/tools/`, verifying every download against the publisher's SHA-256 file and keeping the previous version for rollback. `media` runs yt-dlp as a child process: `-J` to inspect a link, then a download run whose progress arrives as JSON lines on stdout; stderr is mapped to error kinds. A media download is a job with `kind = Media`, scheduled by the existing queue like HTTP jobs. All tests run offline against a fake tool binary served by the testkit.

**Tech Stack:** as M4, plus `zip` 9.2 (`default-features = false, features = ["deflate"]`), `tar` 0.4, `lzma-rust2` 0.25 (`default-features = false, features = ["std", "xz"]`, pure Rust), `libc` (Unix signals), `windows-sys` (Windows console control events). All checked on crates.io on 2026-11-01.

**Spec:** `docs/superpowers/specs/2026-10-27-taurus-v2-design.md` — sections 3 (media in v1.0), 4.1 (Simple add: Video / Audio only, quality), 6.5, 7 "Media", 9 row M5. **Design reference:** canvas artboards `SimpleAdd` (Video/Audio only, Save to, Quality) and the live-recording row in `SimpleMain`.

## Facts this plan relies on (checked 2026-11-01)

- **yt-dlp** release `2026.10.21` assets include `SHA2-256SUMS`, `yt-dlp.exe` (Windows x64), `yt-dlp_arm64.exe`, `yt-dlp_macos` (universal), `yt-dlp_linux`, `yt-dlp_linux_aarch64`, `yt-dlp_musllinux`, `yt-dlp_musllinux_aarch64`. Stable download URLs: `https://github.com/yt-dlp/yt-dlp/releases/latest/download/<asset>`. The release notes warn that old executables' self-updater (`-U`) is open to man-in-the-middle attacks, so **we never use `-U`**; we update by downloading the new asset and checking it against `SHA2-256SUMS` ourselves.
- yt-dlp options used: `-J`/`--dump-single-json`, `--flat-playlist`, `--newline`, `--progress-template [TYPES:]TEMPLATE` (fields under `info` and `progress`), `--print`, `--js-runtimes RUNTIME[:PATH]` (only `deno` enabled by default), `--ffmpeg-location PATH`, `--live-from-start` (experimental; YouTube, Twitch, TVer, mellow-fan), `--wait-for-video MIN[-MAX]`, `--windows-filenames`, `--merge-output-format`, `-x`/`--audio-format`/`--audio-quality`, `--embed-thumbnail`, `--embed-chapters`, `--embed-metadata`. `--remote-components` is "not needed if you are using an official executable".
- **Deno** release `v2.9.8` assets: `deno-{x86_64,aarch64}-{unknown-linux-gnu,apple-darwin,pc-windows-msvc}.zip`, each with `<asset>.sha256sum`. URL: `https://github.com/denoland/deno/releases/latest/download/<asset>`.
- **ffmpeg** for Linux and Windows: `yt-dlp/FFmpeg-Builds` release `latest`: `ffmpeg-master-latest-{linux64,linuxarm64}-gpl.tar.xz`, `ffmpeg-master-latest-{win64,winarm64}-gpl.zip`, checksums in `checksums.sha256`. URL: `https://github.com/yt-dlp/FFmpeg-Builds/releases/latest/download/<asset>`.
- **ffmpeg** for macOS: `https://ffmpeg.martin-riedl.de/redirect/latest/macos/{arm64,amd64}/release/{ffmpeg.zip,ffprobe.zip}` with a `.sha256` file next to each resolved download; binaries are signed. Intel macOS release builds end January 2027 — keep the last installed version working after that.

## Global Constraints

- All earlier Global Constraints hold. No test touches the internet; tools are served by `taurus-testkit`.
- Tools live in `data_dir/tools/<tool>/<version>/`; `data_dir/tools/<tool>/current` (a text file) names the active version; the previous version directory is kept for rollback, older ones are deleted.
- A tool download is accepted only if its SHA-256 matches the publisher's checksum file, and the installed binary then answers its version command (`yt-dlp --version`, `ffmpeg -version`, `deno --version`) within 10 s. Otherwise the new version is deleted and the previous one stays active.
- yt-dlp update checks: at most once per 24 h (on the first media job of the day), and immediately when a run fails with an "extractor broke" pattern (Task 4). ffmpeg and Deno: at most once per 7 days.
- Every yt-dlp run gets `--js-runtimes deno:<path>`, `--ffmpeg-location <dir>`, `--windows-filenames`, `--no-warnings`, `--newline`, `--no-colors`.
- Simple defaults: video `-f "bv*+ba/b"` merged to MP4 (`--merge-output-format mp4`), audio-only `-x` (best audio, original codec), `--embed-thumbnail --embed-chapters --embed-metadata`, no subtitles. Playlists over 50 entries need confirmation (`AddRequest::confirm_large_playlist`).
- Output names: single `%(title).200B [%(id)s].%(ext)s`; playlist `%(playlist_title).100B/%(playlist_index)03d - %(title).150B [%(id)s].%(ext)s`, inside the job's `dest_dir`.
- Pause/stop: Unix sends `SIGINT`, Windows sends `CTRL_BREAK_EVENT` to a child started with `CREATE_NEW_PROCESS_GROUP`; after 10 s without exit, kill. yt-dlp resumes its `.part` files on the next run.
- New error kinds and their Simple wording are added to `messages.slint` and the notification table in the same task (no kind without a message).

## Review Focus

1. A tampered or half-downloaded tool must never run: checksum mismatch or a failing version command leaves the previous version active. Test: Task 2 `bad_checksum_keeps_previous`, `broken_binary_rolls_back`.
2. Pausing a media download and resuming must continue from yt-dlp's partial file, not restart, and must not leave the process running. Test: Task 5 `pause_interrupts_and_resume_continues`.
3. Stopping a live recording must leave a playable file, even if yt-dlp exits without finalizing. Test: Task 5 `stop_recording_keeps_file`.
4. A YouTube breakage ("Signature extraction failed" etc.) must trigger an immediate yt-dlp update and one automatic retry, not a dead job. Test: Task 4 `extractor_break_updates_and_retries`.
5. Offline first use must not hang or fail cryptically: the job waits with "Getting video tools…" and retries later. Test: Task 2 `offline_install_is_transient` + Task 5 `media_job_waits_for_tools`.

Mapping (case-insensitive substring on the ERROR line):
- `Private video`, `Video unavailable`, `This video has been removed`, `has been terminated` → MediaUnavailable
- `not available in your country`, `geo restricted`, `geo-restricted` → MediaRegionLocked
- `Sign in to confirm your age`, `age-restricted`, `members-only`, `Join this channel`, `requires authentication`, `login required` → NeedsSignIn
- `Sign in to confirm you're not a bot`, `confirm you are not a bot` → BlockedByBotCheck
- `HTTP Error 429`, `Too Many Requests` → RateLimited
- `Unsupported URL` → SiteNotSupported
- `Unable to download`, `timed out`, `Connection reset`, `getaddrinfo`, `Temporary failure in name resolution`, `Network is unreachable` → ConnectionLost
- `Signature extraction failed`, `nsig extraction failed`, `Unable to extract`, `Requested format is not available` (the last one only when a non-custom quality was used) → Unknown with extractor broke = true
- ffmpeg merge/postprocess errors (`Postprocessing:`, `ffmpeg exited with code`) → ToolFailed
- otherwise Unknown

Simple messages (added to `messages.slint` and the notification table): `media_unavailable` "This video is private or was removed." · `media_region_locked` "This video isn't available in your country." · `tool_failed` "The video tools couldn't finish this file. The pieces were kept in the folder." · `needs_confirmation` "This needs your confirmation." (the playlist question itself is worded in `add.slint`)

Breakage recovery (implemented in Task 5's runner, tested there): on "extractor broke", force a yt-dlp update; if the version changed, retry the run once automatically; otherwise fail with the mapped kind.

Run arguments (in this order, then the URL): global flags; `-f <selector>`; video: `--merge-output-format mp4`; audio-only: `-x` (+ preset args); `--embed-thumbnail --embed-chapters --embed-metadata`; `--no-playlist` unless `playlist`; live: `--live-from-start --wait-for-video 30-600`; `-o <dest>/<template>`; `--progress-template "download:TAURUS-PROGRESS %(progress)j"`, `--progress-template "postprocess:TAURUS-PP %(progress.postprocessor)s %(progress.status)s"`, `--print "after_move:TAURUS-FILE %(filepath)j"`, `--print "before_dl:TAURUS-ENTRY %(playlist_index|0)s %(n_entries|1)s %(title)j"`.

Decisions:
- Add: `Engine::add` on a media link stores `kind = Media`, name = title (playlist title for playlists), `MediaOptions` from the choice (default `best`). A playlist with `count > 50` and `!confirm_large_playlist` → `Err(CoreError { kind: NeedsConfirmation, detail: "playlist:<N>" })` with no job row; the UI asks and adds again with `confirm_large_playlist = true`.
- Scheduling: media jobs count against `max_active` like HTTP jobs. Before running: `ensure` all three tools (phase GettingTools, `Event::ToolStatus` forwarded); a transient tool error → Waiting (existing retry path). Daily yt-dlp update check runs here too.
- Progress: parse `TAURUS-PROGRESS {json}` → `downloaded_bytes`, `total_bytes` or `total_bytes_estimate`, `speed`; playlist progress = `(entries_done + current_fraction) / entries_total` scaled to bytes when totals are known, else `downloaded` only; `TAURUS-PP` lines set phase Merging/Converting; `TAURUS-FILE` records each finished file (kept in `JobView.media` for "Open"); `TAURUS-ENTRY` updates entries.
