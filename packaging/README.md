# Packaging

Hyades ships as an NSIS installer (Windows), a `.app` bundle (macOS), and a
deb, an AppImage and an rpm (Linux). The packages are built with
[cargo-packager](https://github.com/crabnebula-dev/cargo-packager) 0.11.8 and
[cargo-generate-rpm](https://github.com/cat-in-136/cargo-generate-rpm) 0.21.1:

```sh
cargo install --locked cargo-packager@0.11.8 cargo-generate-rpm@0.21.1
```

## Files

| File | What it is |
|---|---|
| `packager-common.toml` | The values every OS config shares: name, version, identifier, publisher, description, homepage, license, icons, category, binaries. |
| `packager-linux.toml` | deb and AppImage: the common values, plus the `magnet:` link handler, the `.torrent` file type, the deb's library dependencies and the AppStream metainfo. |
| `packager-windows.toml` | NSIS installer: the common values, plus a per-user install, the installer icon, no downgrades, and an uninstaller that never offers to delete download data. |
| `packager-macos.toml` | `.app` bundle: the common values, plus macOS 11.0 as the minimum. |
| `linux/dev.nikethai.hyades.desktop` | The desktop entry the rpm installs as `/usr/share/applications/hyades.desktop` (cargo-packager names the deb's and the AppImage's entry `hyades.desktop` too). `check-linux.sh` checks the deb's and the AppImage's entries against it. |
| `linux/dev.nikethai.hyades.metainfo.xml` | AppStream metainfo (component id `dev.nikethai.hyades`, launchable `hyades.desktop`), installed to `/usr/share/metainfo/` by every Linux package. Its `<release>` is the app's version. |
| `macos/entitlements.plist` | The (empty) entitlements `.github/workflows/release.yml` signs `Hyades.app` with when an Apple certificate is set; the hardened runtime needs no exceptions. |
| `check-linux.sh` | Checks the built Linux packages (see below). |
| `icons/` | The app icon: PNGs from 32 to 1024 px, `hyades.ico` and `hyades.icns` (generated by `cargo xtask icons`). |
| `update-key.pub` | The minisign public key that checks in-app updates. |

The rpm is described in `[package.metadata.generate-rpm]` in
`apps/taurus-desktop/Cargo.toml`. On Windows, `apps/taurus-desktop/build.rs`
embeds `icons/hyades.ico` and the version info (product name and file
description "Hyades") in `hyades.exe`.

The Inter font (`apps/taurus-desktop/ui/fonts/`, SIL Open Font License 1.1)
is compiled into the binary, so no package installs a font file. Its
copyright and licence travel inside the font data; the licence text is
`apps/taurus-desktop/ui/fonts/OFL.txt`.

### How cargo-packager 0.11.8 reads these configs

- It reads a single file per `--config`, with no include, so each
  `packager-<os>.toml` starts with the lines of `packager-common.toml`
  verbatim. Change a shared value in all four files.
  `apps/taurus-desktop/tests/packaging.rs` fails when they differ, or when
  `version` is not the version in `apps/taurus-desktop/Cargo.toml` (with
  `--config`, cargo-packager does not read `Cargo.toml`, so a version bump
  updates the configs too, and the metainfo's `<release>`).
- `icons` lists `icons/hyades.icns` beside the PNGs: the macOS packager
  copies a listed `.icns` as is, and from PNGs alone it fails on `1024.png`
  and `64.png` ("No matching IconType"). The deb and the AppImage skip it;
  the Windows installer takes `hyades.ico`.
- It resolves relative paths from the config file's folder, `packaging/`:
  `icons/*.png` is `packaging/icons/*.png`, and `../LICENSE` is the repo's
  `LICENSE`.
- It accepts `--binaries-dir` but does not use it. The configs therefore set
  `binaries-dir = "../target/release"`, so the packager takes `hyades` from
  `target/release/`. After a build with `--target <T>`, copy the binary from
  `target/<T>/release/` to `target/release/` first (on macOS, `lipo` can write
  the universal binary there directly).

## Building

All commands run from the repo root. Build the app first:

```sh
cargo build --release -p taurus-desktop [--target <T>]
```

cargo-packager takes the binary from `target/release/` (the configs'
`binaries-dir`). **After a `--target <T>` build, put it there first**, or
cargo-packager fails with "Failed to copy file … hyades":

```sh
mkdir -p target/release
cp target/<T>/release/hyades target/release/        # hyades.exe on Windows
# macOS universal: lipo -create … -output target/release/hyades
```

Then, per OS. cargo-packager resolves a relative `--out-dir` from the
config's folder (`packaging/`), so pass an absolute path:

```sh
# Linux: deb and AppImage, then the rpm
cargo packager -c packaging/packager-linux.toml --out-dir "$PWD/dist/linux"
cargo generate-rpm -p apps/taurus-desktop [--target <T>] -o dist/linux/

# Windows: NSIS installer
cargo packager -c packaging/packager-windows.toml --out-dir "$PWD/dist/windows"

# macOS: Hyades.app
cargo packager -c packaging/packager-macos.toml --out-dir "$PWD/dist/macos"
```

The deb's version must use `~` for a prerelease (`1.0.0~rc.1`, not
`1.0.0-rc.1`): dpkg reads `-rc.1` as a revision, which sorts above `1.0.0`.
The workflows rewrite `version` in `packager-linux.toml` that way before
packaging; do the same for a local prerelease deb (`check-linux.sh` refuses a
deb whose version holds a `-`).

`dist/` is ignored by git. cargo-generate-rpm finds the binary under
`target/<T>/release/` by itself (with `--target`) and needs no copy.

The AppImage step downloads `linuxdeploy` and `AppRun` from GitHub releases
into `~/.cache/.cargo-packager/AppImage/` the first time (`XDG_CACHE_HOME`
moves it). If that download fails behind a TLS-intercepting proxy, fetch the
three files named in the error into that folder with `curl` and run again.

## Checking the Linux packages

```sh
packaging/check-linux.sh dist/linux
```

It needs `dpkg-deb` and `rpm` (`sudo apt-get install rpm`) and prints `ok`,
or what is wrong and exits 1. It checks that:

- the deb's version holds no `-` (see above);
- the deb holds `usr/bin/hyades`, `usr/share/applications/hyades.desktop`
  and a 256x256 icon;
- the deb's desktop entry has `Name=Hyades`, `Exec=hyades %u` (or `%U`) and
  the same `MimeType` list as `linux/dev.nikethai.hyades.desktop`
  (`x-scheme-handler/magnet` and `application/x-bittorrent`);
- the deb's metainfo names `hyades.desktop` as its launchable, and that entry
  is in the package;
- the rpm holds `/usr/bin/hyades` and `/usr/share/applications/hyades.desktop`;
- the AppImage, extracted with `--appimage-extract` (no FUSE needed), holds
  `usr/bin/hyades`, and a `hyades.desktop` and a metainfo passing the same
  checks as the deb's.

To try a package without installing it:

```sh
xvfb-run -a timeout 5 squashfs-root/AppRun   # after hyades_*.AppImage --appimage-extract
```

Exit code 124 (stopped by `timeout`) with no panic on stderr means the app
started.

## Release builds and dry runs

`.github/workflows/release.yml` builds every platform (Linux x64/arm64,
Windows x64/arm64, macOS universal) with the flow above, renames the
packages to the release asset names and uploads each platform's files as a
workflow artifact `dist-<platform>`.

- **Dry run on a pull request:** any pull request that changes
  `.github/workflows/release.yml`, `packaging/**` or
  `apps/taurus-desktop/Cargo.toml` runs the workflow as a dry run. It builds,
  packages and checks everything (including `check-linux.sh`) and uploads the
  artifacts; it never publishes, and it never uses the SignPath or Apple
  secrets (macOS is signed ad hoc). To start one, open a pull request (a
  draft is fine) that touches one of those paths; the packages are under the
  run's *Artifacts*. A new push to the pull request cancels the older run.
- **Manual run:** Actions → Release → *Run workflow*, with `dry_run` checked
  (the default). This works only once `release.yml` is on the default branch.
  It uses the signing secrets that are set.
- **Release:** pushing a tag `v<version>` (the version in
  `apps/taurus-desktop/Cargo.toml`) builds, signs `latest.json` and
  `SHA256SUMS` with the minisign key, checks `latest.json` against
  `update-key.pub`, and creates a draft release.
- **Prereleases and the updater:** installed copies fetch
  `releases/latest/download/latest.json`, and GitHub's `latest` never names a
  prerelease, so a prerelease's manifest is never offered: a `1.0.0-rc.1`
  copy is offered `1.0.0` but never `1.0.0-rc.2`.
